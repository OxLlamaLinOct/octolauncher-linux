Error 132 Postmortem

How a 20-year-old race condition in the 1.12 client only ever loses on many-core CPUs — and how to fix it in five minutes.

Symptom ERROR #132 (0x85100084)
Client Vanilla 1.12 / TurtleWoW-derived, build 5875
Platform Linux · Proton / Wine
Status Root cause confirmed, fix verified

If you just want the fix

Your CPU almost certainly has a lot of logical cores (workstation or server-class, 32+ threads). Pin the game to one core and tell it there's only one core, and it stops crashing:

shell
taskset -c 0 env WINE_CPU_TOPOLOGY=1:1 wine WoW.exe

Launching through Proton/a launcher wrapper instead of raw wine? Set WINE_CPU_TOPOLOGY=1:1 in the environment and prefix the whole launch command with taskset -c 0. On real Windows, the equivalent is Task Manager → Details → right-click WoW.exe → Set Affinity → one CPU.

01Is this you?

This specific failure has a distinctive shape. Check the boxes before assuming it's the same bug.

  • The game goes to a black window and dies within a few seconds — before the login screen ever paints.
  • The crash dialog reads "ERROR #132 (0x85100084) Fatal Exception," ACCESS_VIOLATION, referencing a very small memory address (commonly 0x00000009).
  • Your CPU has an unusually high logical core count — think dual-socket Xeon, Threadripper, or any workstation/server board, not a typical 4–16 core desktop.
  • It happens no matter what you change: mods, DXVK on or off, different Proton/Wine versions, a completely fresh client download.

That last result matters: it's not that fewer cores helps, it's that one core does. With real two-core parallelism, two threads can genuinely execute at the same instant and hit the race window; pinned to a single core, the OS has to time-slice between them instead, which was enough on its own to stop it from losing.

03What's actually happening

The client's own crash reporter (Errors/*.txt, dropped next to WoW.exe) turned out to hold a full register dump and stack trace — the real breakthrough. Cross-referencing it against the client binary's own import table pinned the exact Win32 call.

The fault: EXCEPTION_ACCESS_VIOLATION reading address 0x9, inside ntdll.dll, at an instruction that turned out to be KERNEL32.dll::LeaveCriticalSection's real implementation:

ntdll.dll · disassembly at fault0x7BF678EA
; EBX holds the argument WoW.exe pushed - a corrupt CRITICAL_SECTION*
mov ebx, [ebp+8]
mov eax, [ebx+8]      <- crash: ebx=1, so this reads address 0x9
dec eax
mov [ebx+8], eax
test eax, eax

Walking backward from there into WoW.exe itself turned up a real, textbook bug in the client's own 20-year-old code: a hand-rolled lazy-initialized critical section, guarded by a proper spinlock — except the pointer to it gets published before initialization finishes, and a separate code path elsewhere reads that same pointer with no guard at all before calling LeaveCriticalSection on it.

Thread A
(lazy init)
acquire spinlock
→
publish pointer
→
InitializeCriticalSection()
→
release spinlock
Thread B
(unguarded)
read pointer, no check
→
LeaveCriticalSection()

On real Windows, and on typical 4–16 core Linux desktops, Thread B essentially never gets scheduled inside that window — the race is real but the odds of losing it are vanishingly small. A CPU with dozens of logical cores changes the scheduling distribution enough that it's hit reliably instead of almost never.

Vanilla WoW was built years before multi-core CPUs were mainstream, and it shows: the client never scales its real work across more than a couple of small helper threads (a timing-calibration thread, audio, basic network I/O). That's also why the fix below costs nothing — there's no real parallelism to lose.

04The fix

Two things need to be true at once: the app has to believe it's on one core, and the OS actually has to schedule it on only one. Topology-faking alone wasn't enough, and neither was a real cap of 2 or 4 cores — on tested affected hardware, exactly one core is the threshold, not "a small number."

Any Linux + Wine/Proton setup

Wrap your normal launch command:

taskset -c 0 env \
  WINE_CPU_TOPOLOGY=1:1 \
  wine WoW.exe

Real Windows, many-core hardware

Task Manager → Details tab → right-click WoW.exe → Set affinity → uncheck all but one CPU. Do this every launch, or script it.

If you're on OctoLauncher specifically: current builds detect systems above 32 logical cores automatically and apply this for you — nothing to configure.

Honest caveat

One detail never fully closed: the corrupt pointer's observed value was the literal integer 1, but an exhaustive scan of every reference to that global across the entire client binary found no code that ever writes 1 there — only the correct address. The race window (pointer published before init) is real and directly demonstrated in the disassembly; exactly how it manifests as 1 specifically, rather than a mid-init address, wasn't pinned down. It didn't need to be — the fix was verified empirically, independent of that last detail.

05Who else this applies to

Nothing about the root cause is specific to OctoWoW, or even to this one server. It's a bug in the base 1.12 client binary itself. If you're on a many-core machine and hitting ERROR #132 on any vanilla/classic private server — Turtle WoW, or anything else built on the same client — the same fix almost certainly applies.

More generally: this is a useful pattern to recognize in any old 32-bit Windows software under Wine that crashes only on unusually many-core hardware. Hand-rolled thread-safety code from the single-and-dual-core era is common in software this age, and Wine's scheduling characteristics differing from real Windows is enough on its own to expose races that native Windows almost never triggers.
